# v2: contribution, without giving up the verifiable build

Scoped 2026-09-15. **Not settled.** `DECISIONS.md` carries the open decision; this
file is the plan that would follow if it is taken. Nothing here is v1, and v1 asks
only one thing of it: that the **Account** links come out, because they advertise
an account model this plan probably makes wrong.

Gated on two things that are not negotiable: v1 shipping, and the dual-use policy
existing. The policy is not a nicety here. It is the criterion the review step
applies, so without it the review step has no rule and becomes taste.

## Premise, restated because this is where it erodes

The registry never designates; consumers pin, visibly. **A submission queue is the
most comfortable place in this whole system for quality review to grow**, more
comfortable than a diff, because a queue has a reviewer and a reviewer has
opinions. See the invariant in section 5. It is the most important part of this
document.

## The shape

Three systems, each doing the one thing it is actually good at.

| | job | why not the others |
|---|---|---|
| **Supabase** | identity, submission writes, the pending state | Postgres, auth, RLS and storage hosted, no server to run. Already named as the successor in `DECISIONS.md` 2026-09-12 |
| **Git** | the published snapshot | It is the thing anyone can rebuild and diff, which is what makes the falsifier mean something |
| **HF Hub** | artifact bytes | Already settled. `served_repo` and `served_commit` exist for it, `fetch.py` already resolves `resolve/{sha}/{path}`, and HF repos are git so commit pinning is real |

**The property being defended is not "no backend".** It is that the published
corpus is a file in git that anyone can rebuild, diff and re-derive. Where writes
happen is orthogonal to that, and conflating the two is the mistake that produced
the first version of this plan.

### One refinement to the 2026-09-12 decision

That entry says "Postgres or Supabase later is a driver swap" behind `db.py`. In
this shape it is not a swap. SQLite stays exactly where it is, as the build-time
read store. Supabase is **added alongside** as the write store. `db.py` remains the
one seam for reads and gains no Postgres driver. That is a refinement of the entry,
not a contradiction of it, and it is cheaper than what the entry anticipated.

## 1. Identity, and the problem nobody has noticed yet

`author` is free text today: `alice`, `bob`, `soham`. On a public registry that is
namespace squatting waiting to happen, and nothing in the schema addresses it.

**But `author` cannot simply become "a verified account".** Three cases break it,
and the lane decided on 2026-09-15 removes the strongest one without removing the
problem.

- **Deferred rather than gone.** The seeding decision says the corpus gets
  populated by indexing the literature, and an entry for someone else's published
  direction has an author who never signed up and may never. That lane is deferred,
  not reversed, so requiring an account would foreclose a plan still on the books.
  Building the cheap version that forecloses it is how a deferral becomes a
  cancellation by accident.
- **It is already false today.** soham's three real submissions were hand-entered
  by the build, not submitted through a form, and the five fixture authors are
  synthetic. Every row in the corpus right now has an author with no account.
- **Evidence is written about other people's work.** An attack card, an
  independent evaluation and a support card all name an author who is not the
  submitter. Those will have accounts; their subjects may not.

So `author` stays a namespace string, and **claiming is a separate object**:

- A namespace starts **unclaimed**. Indexed entries live there. The page says so.
- A claim binds an account to a namespace. Evidence is one of: the HF or GitHub
  repo the artifact was published from, a DOI on the paper, or a human decision
  recorded with its reason.
- A claimed namespace shows who holds it. An unclaimed one shows that it is
  unclaimed, which is a fact rather than a gap, same as every other absence here.

This is also the honest answer to squatting: the namespace is not the claim, the
claim is the claim.

**Provider: HF, and it is verified rather than assumed.** A steering-vector author
has an HF account, and HF orgs give the same organisation-level trust GitHub orgs
do. This was the one blocking unknown in this document and it resolved on
2026-09-16, better than assumed.

HF is a full OIDC provider, discovery at
`huggingface.co/.well-known/openid-configuration`, RS256, PKCE via S256, usable
from any site rather than only from a Space. Supabase takes custom OAuth2/OIDC
providers alongside its built-ins. An app was registered and a device-code flow
run end to end with scopes `openid profile read-memberships`, returning:

    sub                 62cf4580e7f6014c0ea2450f
    preferred_username  sohampadia
    orgs                [{name: controlbun, sub: ..., roleInOrg: admin}]

So a claim on `allenai/...` means `allenai` appears in `orgs`, and `roleInOrg` is
there if a finer rule is ever wanted.

**But the claim does not survive into Supabase, and that is load-bearing.** After
a real sign-in through the configured provider, `auth.users.raw_user_meta_data`
holds `preferred_username` and `sub` and **`orgs` is null**. `orgs` is an
HF-specific claim rather than a standard OIDC one, so it does not make the trip.

This is better than it looks, because storing membership at signup was always
wrong. People join and leave organisations. A membership checked once and cached
forever is a stale fact wearing a verified badge, and the drop removes the option
of doing the lazy thing.

**So memberships are captured, dated, and re-verified rather than stored.** Call
HF's userinfo endpoint while the token is live, record what `orgs` said **and
when**, and treat it as dated evidence. That is the rule this project already
applies to the history audit and the attestations: the result is dated, not
permanent.

**The timing is forced by Supabase.** `provider_token` is returned in the session
immediately after OAuth sign-in and is not persisted across refreshes. So the
userinfo call happens at sign-in, not weeks later at claim time, and re-verifying
means the user signs in again rather than the app trusting a cache. A claim page
that says "membership of `allenai` confirmed on 2026-09-16" is honest; one that
says "verified" is not.

**Bind the claim to `sub`, not to `preferred_username`.** HF handles are
renameable. A claim bound to the handle either breaks when someone renames or,
worse, follows the handle to whoever takes it next. `sub` is stable and opaque.
The namespace string stays the handle, because that is what a reader sees and
what `author/label@version` is made of; what the claim records is the `sub`.

**One correction to what this document assumed.** It said a serverless function
might be needed for the OAuth secret exchange. It is not: Supabase is the
confidential client and performs the exchange itself. The app is registered with
a secret rather than as a public PKCE app, because HF's discovery advertises only
`client_secret_basic` and `client_secret_post`, not `none`, and Supabase reads
that document. Still no function, still no server of ours.

GitHub as a second provider costs nothing, is built in, and covers the case where
someone's artifacts live on GitHub rather than HF, which is where the arena's own
three came from.

## 2. The write path

A form on the static site, posting to Supabase. No server, because Supabase is the
server. One serverless function only if the OAuth flow needs a client secret,
which is not a backend.

**What a submission has to carry**, from the schema as it already stands:
`definition`, which is NOT NULL and load-bearing because it is the thing other
authors disagree with; the model id, layer with its indexing convention, and hook
point; and shape and dtype.

**Bytes are pointer-first.** Supabase gives 1 GB of file storage on the free plan,
so it cannot be the primary store and should not pretend to be. The settled
position already says SAE latents are pointer-only and everything else is upload
preferred, pointer available. In practice: the submitter names a repo, commit and
path, and our HF org mirrors it when rights are resolved, which is what
`served_repo` and `served_commit` were added for.

**Validation happens at write time, not at review time.** Built 2026-09-17.
Shape, dtype, L2 norm and sha256 are compared against the actual bytes before a
row is accepted, by `controlbun.artifact.confirmed`, which `client._check` and
both falsifier checks also call so there is one comparison rather than three. A
row whose metadata disagrees with its bytes never enters the queue, so the
reviewer never sees it and never has to judge it.

**Checked, not recomputed, and the difference is load-bearing.** This section
said "recomputed" and that would have been the wrong build. A submitter's shape
and norm may be cited from the paper or the extraction script, and a write path
that quietly overwrote them with its own arithmetic would store values that
agree with the bytes by construction and discard the fact that the citation and
the bytes agreed. The submitter claims, the bytes confirm, a mismatch is a
refusal naming both sides, and a submitter with nothing to claim gets the
derived value. See `DECISIONS.md` 2026-09-17.

This is also where **S1** gets paid off: the content hash the review found missing
is what write-time validation produces, and it belongs in the schema before there
is a write path rather than after.

## 3. The publish step

```
fixtures/build.py      synthetic corpus          (exists)
artifacts/seed.py      real, hand-entered        (exists)
supabase/pull.py       approved rows             (new)
controlbun.export        the committed snapshot    (exists)
make verify            invariants, falsifier     (exists)
```

`controlbun.json` is already committed under `astro/src/data/`. v2 adds one puller
and changes nothing downstream of it. The site keeps building from a file.

**The falsifier runs before the commit, and a row that fails it is never
published.** That is the gate, and it is not a quality gate: it checks that
published numbers re-derive from raw artifacts and that nothing on a page traces to
nowhere. A submission can be wrong, badly argued, or poorly evidenced and still
pass, which is correct.

Publishing is a human running the build and committing, or CI once `CLAUDE.md`'s
repo section is amended for v1 anyway. Either way the commit is the audit trail:
what was published, when, and by whom, diffable.

## 4. What does not get built

Worth listing, because the instinct with a backend is to move everything behind it.

- **Reading.** Static, unchanged.
- **Search.** Pagefind, client-side, unchanged.
- **Artifact resolution.** `fetch.py`, unchanged.
- **The client package.** Reads the committed snapshot. Unchanged.
- **Comparison.** Derived on demand at build time, never stored. A comparisons
  table is an opinion with a schema, and that has not changed.

## 5. Review, and the invariant that has to hold it

Two criteria, and the list is closed:

1. **Schema validity**, already automated. `make verify` decides this and a human
   does not.
2. **Dual-use**, which is policy. This is the entire human judgment.

**Quality is not a criterion.** Not clarity of the definition, not adequacy of the
confound axes, not whether the vector looks good. A submission that passes the
falsifier and the policy gets published even if the reviewer thinks it is weak,
because the reviewer thinking it is weak is a claim they can publish as an attack
card like anybody else.

### How to make that mechanical

Prose will not hold it. Three things that might:

- **Decline reasons are a closed set, published.** This is the one place a closed
  enum is legitimate in this schema, and the reason is instructive: every other
  closed enum constrains contributors, and this one constrains the registry.
  Enumerating what we may refuse for is the inverse of the usual failure. The
  trip-wire list in `CLAUDE.md` should say so explicitly, or someone will delete
  this on principle.
- **An invariant test that no decline reason references an eval result.** The same
  scan that already refuses ordering by `trait_score` or `coherence_score`, pointed
  at the decline vocabulary.
- **A published decline log.** Count and reason category, never the content of a
  declined submission. If the reasons drift toward quality, it is visible from
  outside rather than only to the person drifting.

## 6. Open, and blocking

- **Uploads at all, or pointer-only forever?** Pointer-only is simpler, cheaper,
  keeps "we only pointed at it" available as an answer, and makes the registry
  useless to anyone whose artifact is not already hosted somewhere. Unresolved.
- **Namespace claiming.** Evidence types above are a sketch. The dispute case,
  two people claiming one namespace, has no answer yet.
- **Review capacity.** One person, and an indexed corpus of a few hundred plus
  whatever arrives. A queue nobody drains is worse than no queue, because it
  accepts submissions and then loses them.
- **Whether anyone wants this.** Still the largest open question in the project,
  still unanswered, and the five-person question in the lab is still the cheapest
  way to answer it. Building a contribution path before knowing is the expensive
  order to do these in, and the lane without indexing makes it the load-bearing
  question rather than a background one: with no indexed corpus, contribution is
  the only way the registry ever holds anything it did not put there itself.

## 7. Risks

**The erosion trap, again, because it is the one that matters.** A queue with a
reviewer is where "the registry never designates" dies, one reasonable decision at
a time. Section 5 is the mitigation and it is not obviously sufficient.

**Free tier pauses after one week of inactivity.** Checked 2026-09-15: 500 MB
database, 1 GB storage, 50,000 monthly active users, 5 GB egress, two active
projects, paused after a week idle. Pro is $25/month and never pauses.

This is an argument *for* the split rather than against Supabase. A pause takes
down submissions and leaves the site completely unaffected, because the site reads
a committed file. That is the right failure mode, and it would be the wrong one if
the read path went through Postgres.

**Supabase becomes load-bearing, and it is a vendor.** Mitigated by it holding only
the write path and the pending queue. The published corpus is in git, so the worst
case is that contribution stops and nothing is lost.

**HF is not the backend, on purpose.** Storage and identity yes; metadata and
accounts no. If identity, storage and metadata all live on HF then this is an HF
feature, and the company most likely to ship a steering-artifact registry would own
the user relationship. GitHub will never ship one. That asymmetry does not apply to
bytes, because bytes are not a relationship. Neuronpedia also already holds the
"atlas on top of HF" position, with 50 million latents there.
